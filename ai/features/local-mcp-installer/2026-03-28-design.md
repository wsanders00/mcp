# Local MCP Installer Design

**Date:** 2026-03-28

## Goal

Add a fork-only installer under `install/` that helps team users set up selected MCP servers from this
repository for on-demand agent use, while keeping all installer logic out of server source trees except
where `src/oci-iot-mcp-server` may need installer-related adjustments.

## Constraints

- The installer may install MCP servers from this local repo only.
- No changes are allowed to any MCP server besides `src/oci-iot-mcp-server`.
- All installer code and generated artifacts must live under top-level `install/`.
- The installer must ask the user which repo servers to install, with `all` as an option.
- `all` means all Python-based servers supported by the installer, not the Java toolkit.
- The runtime model is one shared Python runtime for all selected servers.
- The primary targets are Codex and VS Code.
- The installer must generate configuration artifacts and instructions, but must not write directly to
  user config locations.
- Generated artifacts must be safe for agent use: only ready servers should be emitted into generated
  Codex/VS Code config.
- This installer is fork-only and will not be proposed upstream.

## In Scope

- Add an installer owned entirely by `install/`.
- Support local installation of selected Python-based MCP servers from `src/`.
- Support both packaged console-script servers and script-based Python servers.
- Generate stable launch wrappers for selected servers.
- Generate Codex registration commands and a VS Code `mcp.json` artifact.
- Produce a readiness report showing which selected servers are ready, blocked, or failed.
- Handle installer-owned edge cases such as script-only servers and servers with extra prerequisites.

## Out Of Scope

- Installing any MCP server that is not sourced from this repo checkout.
- Managing published package installs from PyPI or any third-party registry.
- Supporting the Java toolkit in the initial `all` flow.
- Editing `~/.codex`, VS Code user settings, or workspace settings automatically.
- Starting long-lived background services.
- Refactoring non-IoT server packages to make them easier to install.

## Recommended Approach

Use a Python installer with an installer-owned server registry under `install/`.

This approach keeps all fork-only behavior localized, can support mixed repo server shapes without
changing their source packages, and gives one place to manage server metadata, wrapper generation,
selection, readiness checks, and emitted agent configuration.

## Architecture

### Top-Level Layout

```text
install/
  README.md
  installer.py
  servers.toml
  templates/
  generated/
    bin/
    codex/
    vscode/
    reports/
  runtime/
    python/
```

### Responsibilities

- `install/installer.py`
  - Main entry point.
  - Prompts for server selection.
  - Builds or reuses the shared runtime.
  - Installs selected servers from local repo paths.
  - Generates wrappers, config artifacts, and reports.
- `install/servers.toml`
  - Single source of truth for which repo servers the installer supports.
  - Encodes installation and launch metadata for each server.
- `install/templates/`
  - Static templates for generated scripts, Codex command files, VS Code config, and report output.
- `install/generated/bin/`
  - Stable launch wrappers referenced by agent-facing config.
- `install/generated/codex/`
  - Ready-to-run `codex mcp add ...` commands and operator instructions.
- `install/generated/vscode/`
  - Generated `mcp.json` and merge/copy guidance.
- `install/generated/reports/`
  - Machine-readable and human-readable readiness summaries.
- `install/runtime/python/`
  - Shared Python environment used by every selected Python-based repo server.

## Server Registry Model

`install/servers.toml` defines the set of installer-supported repo servers.

Each entry includes:

- `id`
- `display_name`
- `source_path`
- `install_mode`
  - `package`
  - `script`
- `launch_mode`
  - `console_script`
  - `python_script`
- `entrypoint`
- `python_version`
- `env_hints`
- `readiness_check`
- `notes`

This registry allows the installer to support servers with different packaging layouts without changing
their source trees.

## Selection Model

The installer prompts the user to choose:

- one or more supported server ids
- or `all`

Selection is resolved against `install/servers.toml`.

`all` means all Python-based installer-supported servers in the registry. It excludes
`oracle-db-mcp-java-toolkit` for now.

If a repo server is not yet supported by the installer, it is omitted from the selectable list rather than
being guessed dynamically. This prevents the installer from emitting agent config for servers it cannot
actually validate.

## Install Strategy

### Shared Runtime

- The installer creates one shared Python runtime under `install/runtime/python/`.
- The runtime targets Python 3.13, matching the dominant repo expectation and `oci-iot-mcp-server`.
- Each selected server is installed into that runtime from its local repo path only.

### Supported Install Modes

#### Package Mode

For servers with a `pyproject.toml` and a console script:

- install from `./src/<server>`
- launch via the installed console script inside the shared runtime

This covers most Python package servers in `src/`.

#### Script Mode

For script-based servers without a package console entry point:

- install their Python dependencies into the shared runtime
- launch via the shared runtime interpreter plus the repo script path

This covers `dbtools-mcp-server`.

## Launch Wrappers

Every ready selected server gets one wrapper in `install/generated/bin/`.

Wrapper responsibilities:

- locate the repo root and shared runtime
- fail fast if the runtime or target install is missing
- set installer-owned defaults where needed
- launch the server in stdio mode

Agent config points only to wrappers. It does not point directly to `src/`, package internals, or `uv`.

This keeps the compatibility surface small and lets the installer change underlying install details
without regenerating entirely different agent-facing patterns.

## Agent Integration

### Codex

The installer does not write Codex config directly.

Instead it generates:

- a shell script with one `codex mcp add <name> -- <wrapper> ...` command per ready server
- a short instruction file explaining how to run those commands and re-run them after reinstall

This relies on the observed local Codex CLI capability:

- `codex mcp add <NAME> -- <COMMAND>...`

Generating commands instead of a guessed Codex config file avoids coupling the installer to undocumented
Codex config internals.

### VS Code

The installer generates:

- `install/generated/vscode/mcp.json`
- a short note describing where to copy or merge it

The generated file contains only ready servers and points each entry at its wrapper in
`install/generated/bin/`.

## Readiness And Validation

Selection alone is not enough. The installer must decide whether a selected server is actually safe to
emit for agent use.

Each selected server goes through:

1. install validation
2. launch-target validation
3. optional server-specific readiness checks

The final report classifies each selected server as:

- `ready`
- `blocked`
- `failed`

Only `ready` servers are emitted into generated Codex/VS Code artifacts.

### Edge Cases

#### `dbtools-mcp-server`

- Uses `requirements.txt` plus a raw Python script.
- Installer support is explicit via `script` mode.
- The wrapper launches the repo script using the shared runtime interpreter.

#### `oracle-db-doc-mcp-server`

- Is Python-based, but requires a documentation index before it can serve requests.
- If selected, the installer may accept a user-provided docs path and build the index, or it may mark the
  server `blocked` until the prerequisite is satisfied.
- If blocked, it must not appear in generated agent config.

This prevents the installer from registering a known-broken server as if it were agent-ready.

## Error Handling

- Missing Python 3.13 or missing `uv`: fail with explicit setup guidance.
- Unsupported selected server id: fail early before touching the runtime.
- Local install failure for one server: continue evaluating remaining selections, but mark the server
  `failed`.
- Blocked prerequisite: classify as `blocked` with remediation steps.
- Wrapper launch failure during validation: classify as `failed` and exclude from emitted config.
- Existing generated artifacts: overwrite deterministically so reruns are reproducible.

## Testing Strategy

### Unit Tests

Add installer-local tests under `install/tests/` for:

- registry parsing
- selection resolution
- wrapper rendering
- Codex command rendering
- VS Code config rendering
- readiness classification

### Integration Tests

Add installer-local integration tests for:

- installing a packaged Python server from `src/`
- installing a script-based server such as `dbtools-mcp-server`
- generating wrappers and config artifacts for a mixed selection
- verifying that blocked servers are excluded from generated config

### Non-Goals For Testing

- Do not modify or re-test server internals outside `install/` unless `oci-iot-mcp-server` needs an
  installer-specific adjustment.
- Do not treat all selected servers as equivalent if their startup prerequisites differ.

## Success Criteria

The design is successful if:

- a user can run one installer entry point from the repo root
- the installer prompts for one, many, or `all`
- selected Python-based repo servers are installed only from this repo
- no non-IoT server source files need editing
- generated wrappers can launch ready servers on demand for agent use
- generated Codex and VS Code artifacts contain only ready servers
- blocked or failed servers are clearly explained in the readiness report

## Open Decisions Deferred To Implementation Planning

- exact file names for generated reports
- whether `installer.py` is the only entry point or whether a tiny `install.sh` wrapper is also worth
  adding
- exact readiness probes per supported server
