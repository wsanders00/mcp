# OCI IoT MCP Server Expansion Design

**Date:** 2026-03-26

## Goal

Expand `src/oci-iot-mcp-server` so the server is meaningfully more useful for AI-driven IoT operations, especially raw command execution, post-command verification, domain access setup, and ingest diagnostics.

## Scope

This design only covers `oci-iot-mcp-server`.

The feature set is:

1. `invoke_raw_command_and_wait`
2. `get_raw_command_by_request_id`
3. `list_recent_raw_commands_for_twin`
4. `get_data_api_token`
5. `derive_domain_context`
6. `get_digital_twin_adapter_full`
7. `wait_for_twin_update`
8. `list_recent_rejected_data_for_twin`

The design also includes related internal cleanup when it directly reduces churn or is required for these tools:

- split the current single-file implementation into focused internal modules
- support `OCID + friendly` identifiers
- fix client caching so it is profile-aware
- expand selected existing output models where the current MCP drops useful SDK fields

## Success Criteria

The server should let an MCP client:

- send a raw command and obtain a final, normalized result instead of stopping at the initial enqueue response
- inspect recent or specific raw command records for a twin
- derive the domain metadata needed to reach the data plane
- mint and return a data-plane token when requested
- inspect full adapter details needed for migration and debugging
- wait for a twin update after a command or telemetry action
- inspect recent rejected ingest events for a twin

All new tools must accept either OCI IDs or friendly identifiers where applicable. Ambiguous friendly matches must fail with a structured error that lists candidates and instructs the caller to retry with a unique identifier.

## Current State

`src/oci-iot-mcp-server/oracle/oci_iot_mcp_server/server.py` currently holds FastMCP registration, OCI client creation, list/get wrappers, and response shaping in one file.

`src/oci-iot-mcp-server/oracle/oci_iot_mcp_server/models.py` currently exposes narrow Pydantic models that omit useful fields already present in the OCI SDK, especially for adapters, domains, and domain groups.

The installed OCI SDK already exposes `invoke_raw_command` in the control plane, but it does not expose the higher-level workflows needed here:

- waiting for terminal raw command outcomes
- looking up raw command records by request ID
- listing recent raw commands for a twin
- listing rejected ingest records
- waiting for data-plane twin updates
- minting a caller-facing data-plane token as an MCP tool

Those workflows require a package-local data-plane client layer in addition to the existing control-plane SDK wrappers.

## Prioritization

### Phase 1: Highest Value Command and Access Foundation

Deliver these together because they share the same resolver, domain-context, token, and data-plane plumbing:

- `derive_domain_context`
- `get_data_api_token`
- `get_digital_twin_adapter_full`
- `get_raw_command_by_request_id`
- `list_recent_raw_commands_for_twin`
- `invoke_raw_command_and_wait`

This phase produces the most immediate operator value. It closes the largest current gap: MCP can issue a raw command only indirectly through future work, but cannot verify what happened after the control-plane request is accepted.

### Phase 2: Observation and Ingest Diagnostics

Deliver these after the Phase 1 foundations:

- `wait_for_twin_update`
- `list_recent_rejected_data_for_twin`

These tools build on the same token, resolver, and data-plane access patterns, but they are secondary to the raw-command verification workflow.

## Recommended Architecture

Keep FastMCP tool definitions in `server.py`, but move implementation logic into focused internal modules. The goal is to preserve the package's public entrypoint while preventing the current file from absorbing eight more tools and multiple access patterns.

### Proposed Internal Modules

- `client.py`
  Creates and caches OCI IoT control-plane clients by profile and encapsulates config loading.

- `control_plane.py`
  Wraps `oci.iot.IotClient` calls used by existing tools and new control-plane operations such as `invoke_raw_command`.

- `resolvers.py`
  Resolves `OCID + friendly` identifiers for twins, domains, and domain groups. Produces either a single resolved resource or a structured not-found or ambiguity error.

- `domain_context.py`
  Builds a normalized domain context by composing IoT domain and IoT domain group reads. This is the source of region, device host, data host, domain short ID, domain-group short ID, and DB token scope.

- `data_plane.py`
  Encapsulates token minting and HTTP calls to the IoT data/ORDS endpoints for raw command records, twin updates, and rejected ingest data.

- `polling.py`
  Holds reusable wait-loop logic, deadline handling, and polling intervals for terminal raw command status and twin-update waits.

- `models.py` or split schema modules
  Expands existing models and adds normalized output schemas for domain context, token responses, raw command records, ambiguity errors, and rejected data rows.

### Boundaries

- `server.py` should only perform tool registration, parameter intake, and delegation.
- `control_plane.py` should never know about friendly-name matching or wait loops.
- `resolvers.py` should not perform network calls unrelated to candidate discovery.
- `data_plane.py` should not resolve names; it should operate on canonical IDs and normalized context.
- `polling.py` should own retry cadence and timeout decisions so wait behavior is consistent across tools.

## Tool Design

### 1. `derive_domain_context`

Purpose:
Return the domain metadata operators need to perform follow-on actions without manually stitching together multiple resources.

Inputs:

- `iot_domain_id` or friendly domain selector

Output:

- `iot_domain_id`
- `iot_domain_display_name`
- `iot_domain_group_id`
- `iot_domain_group_display_name`
- `region`
- `device_host`
- `data_host`
- `domain_short_id`
- `domain_group_short_id`
- `db_token_scope`
- any directly relevant access fields already exposed by the SDK

Behavior:
Resolve the domain, read the domain and its domain group from the control plane, derive the normalized context, and return one operator-friendly object.

### 2. `get_data_api_token`

Purpose:
Return a caller-facing token and expiry metadata for the IoT data plane.

Inputs:

- `iot_domain_id` or friendly selector
- optional derived short IDs if the resolved context is already known

Output:

- `access_token`
- `token_type`
- `expires_at`
- `expires_in`
- the resolved context fields needed to use the token safely

Behavior:
Internally derive or accept domain context, mint the token, and return it to the MCP caller. Token export is explicitly allowed.

### 3. `get_digital_twin_adapter_full`

Purpose:
Return the adapter fields needed for debugging and migration, not only the current summary subset.

Inputs:

- `digital_twin_adapter_id`

Output:

- all useful current adapter metadata, including:
  - `digital_twin_model_id`
  - `digital_twin_model_spec_uri`
  - `inbound_envelope`
  - `inbound_routes`
  - display name, description, lifecycle, tags, timestamps

Behavior:
Use the existing control-plane `get_digital_twin_adapter` call and map the full SDK model into a stable MCP response.

### 4. `get_raw_command_by_request_id`

Purpose:
Fetch the exact raw command record that corresponds to a request ID.

Inputs:

- twin selector (`digital_twin_instance_id` or friendly twin selector)
- `request_id`
- optional time window

Output:

- normalized raw command record fields, including request metadata, terminal status, response data, and timestamps

Behavior:
Resolve the twin, obtain the data-plane token/context, query the raw command record source, normalize the payload, and return a single record or a structured not-found result.

### 5. `list_recent_raw_commands_for_twin`

Purpose:
List recent raw command records in a reliable order for operator review and AI follow-up.

Inputs:

- twin selector
- `limit`
- optional time window

Output:

- normalized rows sorted by `time_created` descending

Behavior:
Resolve the twin, query the data-plane raw command feed, normalize records, sort by true creation time descending, and return the limited result set. Do not rely on list order from the upstream API or inferred record IDs.

### 6. `invoke_raw_command_and_wait`

Purpose:
Close the gap between raw command enqueue and raw command outcome.

Inputs:

- twin selector
- `request_endpoint`
- request payload and format
- optional `response_endpoint`
- request duration
- response duration
- timeout

Output:

- immediate enqueue/request metadata
- resolved request ID
- terminal delivery status if observed
- response payload if observed
- timestamps
- timeout indicator if polling expires before a terminal state is seen

Behavior:

1. Resolve the twin.
2. Build the correct SDK request shape for text, JSON, or binary payloads.
3. Call control-plane `invoke_raw_command`.
4. Extract the identifiers needed to correlate with raw command records.
5. Poll the data plane until:
   - a terminal record is observed
   - the caller timeout expires
   - the response window closes without a terminal update
6. Return one normalized object that explains both the enqueue step and the final observed outcome.

### 7. `wait_for_twin_update`

Purpose:
Support post-command or post-telemetry verification loops.

Inputs:

- twin selector
- optional field selector
- `since`
- timeout

Output:

- the first matching update observed after `since`
- full twin snapshot if no field is specified, or field-specific details if one is specified

Behavior:
Resolve the twin, poll the data-plane twin view, compare updates against `since`, and return the first matching change.

### 8. `list_recent_rejected_data_for_twin`

Purpose:
Surface ingest failures quickly for troubleshooting.

Inputs:

- twin selector
- optional time window
- optional limit

Output:

- normalized rejection rows including:
  - reason code
  - reason message
  - payload pointers or correlation metadata
  - timestamps

Behavior:
Resolve the twin, query the rejection feed, normalize the upstream payload, filter to the requested twin and time window, and sort recent-first.

## Identifier Resolution

All new tools should support friendly selectors in addition to OCIDs.

### Supported Resolution Modes

- exact OCID
- exact display name for twins, domains, and domain groups
- derived short IDs for domains and domain groups where the value can be deterministically derived from canonical metadata

### Ambiguity Rules

If a friendly selector matches multiple resources, the tool must fail with a structured ambiguity error. The error payload should include:

- the input that was ambiguous
- resource type
- candidate rows with OCID and display name
- a short next step such as `Retry with the OCID of the intended resource.`

### Not-Found Rules

If resolution finds no candidates, the tool must fail with a structured not-found error that echoes the input criteria.

## Error Handling

Normalize the major error classes instead of leaking raw SDK or HTTP errors as the primary response shape:

- configuration/authentication error
- resolver not-found
- resolver ambiguity
- control-plane upstream error
- data-plane upstream error
- timeout

Each error should preserve enough debugging detail for logs, but the tool output should prioritize actionable guidance for the MCP caller.

## Compatibility

This work is additive at the tool level.

- existing tool names remain available
- the new tools are added alongside the current ones
- `get_digital_twin_adapter_full` is added rather than replacing the current adapter tool

Internal cleanup may intentionally broaden selected existing outputs where the current MCP unnecessarily drops useful SDK fields. That is an acceptable compatibility change because it is a superset, not a semantic rename.

## Testing Strategy

Testing should be package-local and mostly mocked.

### Unit Tests

Add package-local tests for:

- profile-aware client caching
- twin/domain/domain-group resolution by OCID and friendly inputs
- ambiguity and not-found errors
- domain-context derivation
- token response normalization
- adapter full-model mapping
- raw command polling transitions
- raw command timeout behavior
- recent raw command sorting by timestamp
- twin update wait semantics
- rejected-data normalization

### Integration or E2E Coverage

Add a small number of end-to-end scenarios only for the highest-value flows once the harness can support them:

- invoke a raw command and confirm the tool reports a terminal or timeout outcome
- fetch recent raw commands for a twin

The rest of the behavior should be covered with mocked tests because the package depends on both control-plane and data-plane interactions that are difficult to make deterministic in shared CI.

## Documentation Impact

Update the package README to document:

- the new tools
- friendly identifier support
- ambiguity behavior
- token-return behavior and its security implications
- any required environment or profile assumptions for data-plane access

## Risks and Design Responses

### Risk: control plane and data plane use different access patterns

Response:
keep them in separate internal modules and join them only through normalized domain context.

### Risk: friendly identifiers introduce hidden ambiguity

Response:
centralize resolution and make ambiguity a first-class error, never an auto-pick.

### Risk: `invoke_raw_command` only guarantees request acceptance, not outcome

Response:
the new combined tool must always correlate the initial request with data-plane records before reporting a final result.

### Risk: current single-file structure will become unmaintainable

Response:
perform the internal split as part of this work instead of layering new behavior into the existing file.

## Out of Scope

- touching other MCP server packages
- broad redesign of unrelated existing IoT tools
- adding create/update/delete digital twin workflows beyond what is required for the eight tools above
- introducing interactive prompting in the server itself; errors may recommend next actions, but tool behavior remains request/response
