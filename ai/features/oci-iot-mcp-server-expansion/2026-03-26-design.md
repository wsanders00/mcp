# OCI IoT MCP Server Expansion Design

**Date:** 2026-03-26

## Goal

Expand `src/oci-iot-mcp-server` so the server is meaningfully more useful for AI-driven IoT operations, especially raw command execution, post-command verification, domain access setup, and ingest diagnostics.

## Scope

This design only covers `oci-iot-mcp-server`.

The feature set is:

1. `invoke_raw_command_and_wait`
2. `get_raw_command_by_request_id`
3. `list_recent_raw_commands_for_twin`
4. `get_data_api_token`
5. `derive_domain_context`
6. `get_digital_twin_adapter_full`
7. `wait_for_twin_update`
8. `list_recent_rejected_data_for_twin`

The design also includes related internal cleanup when it directly reduces churn or is required for these tools:

- split the current single-file implementation into focused internal modules
- support `OCID + friendly` identifiers
- fix client caching so it is profile-aware
- expand selected existing output models where the current MCP drops useful SDK fields

## Success Criteria

The server should let an MCP client:

- send a raw command and obtain a final, normalized result instead of stopping at the initial enqueue response
- inspect recent or specific raw command records for a twin
- derive the domain metadata needed to reach the data plane
- mint and return a data-plane token when requested
- inspect full adapter details needed for migration and debugging
- wait for a twin update after a command or telemetry action
- inspect recent rejected ingest events for a twin

All new tools must accept either OCI IDs or friendly identifiers where applicable. Ambiguous friendly matches must fail with a structured error that lists candidates and instructs the caller to retry with a unique identifier.

## Current State

`src/oci-iot-mcp-server/oracle/oci_iot_mcp_server/server.py` currently holds FastMCP registration, OCI client creation, list/get wrappers, and response shaping in one file.

`src/oci-iot-mcp-server/oracle/oci_iot_mcp_server/models.py` currently exposes narrow Pydantic models that omit useful fields already present in the OCI SDK, especially for adapters, domains, and domain groups.

The installed OCI SDK already exposes `invoke_raw_command` in the control plane, but it does not expose the higher-level workflows needed here:

- waiting for terminal raw command outcomes
- looking up raw command records by request ID
- listing recent raw commands for a twin
- listing rejected ingest records
- waiting for data-plane twin updates
- minting a caller-facing data-plane token as an MCP tool

Those workflows require a package-local data-plane client layer in addition to the existing control-plane SDK wrappers.

## Prioritization

### Phase 1: Highest Value Command and Access Foundation

Deliver these together because they share the same resolver, domain-context, token, and data-plane plumbing:

- `derive_domain_context`
- `get_data_api_token`
- `get_digital_twin_adapter_full`
- `get_raw_command_by_request_id`
- `list_recent_raw_commands_for_twin`
- `invoke_raw_command_and_wait`

This phase produces the most immediate operator value. It closes the largest current gap: MCP can issue a raw command only indirectly through future work, but cannot verify what happened after the control-plane request is accepted.

### Phase 2: Observation and Ingest Diagnostics

Deliver these after the Phase 1 foundations:

- `wait_for_twin_update`
- `list_recent_rejected_data_for_twin`

These tools build on the same token, resolver, and data-plane access patterns, but they are secondary to the raw-command verification workflow.

## Recommended Architecture

Keep FastMCP tool definitions in `server.py`, but move implementation logic into focused internal modules. The goal is to preserve the package's public entrypoint while preventing the current file from absorbing eight more tools and multiple access patterns.

### Proposed Internal Modules

- `client.py`
  Creates and caches OCI IoT control-plane clients by profile and encapsulates config loading.

- `control_plane.py`
  Wraps `oci.iot.IotClient` calls used by existing tools and new control-plane operations such as `invoke_raw_command`.

- `resolvers.py`
  Resolves `OCID + friendly` identifiers for twins, domains, and domain groups. Produces either a single resolved resource or a structured not-found or ambiguity error.

- `domain_context.py`
  Builds a normalized domain context by composing IoT domain and IoT domain group reads. This is the source of region, device host, data host, domain short ID, domain-group short ID, and DB token scope.

- `data_plane.py`
  Encapsulates token minting and HTTP calls to the IoT data/ORDS endpoints for raw command records, twin updates, and rejected ingest data.

- `polling.py`
  Holds reusable wait-loop logic, deadline handling, and polling intervals for terminal raw command status and twin-update waits.

- `models.py` or split schema modules
  Expands existing models and adds normalized output schemas for domain context, token responses, raw command records, ambiguity errors, and rejected data rows.

### Boundaries

- `server.py` should only perform tool registration, parameter intake, and delegation.
- `control_plane.py` should never know about friendly-name matching or wait loops.
- `resolvers.py` should not perform network calls unrelated to candidate discovery.
- `data_plane.py` should not resolve names; it should operate on canonical IDs and normalized context.
- `polling.py` should own retry cadence and timeout decisions so wait behavior is consistent across tools.

## Configuration Assumptions

The new data-plane features require two different credential models:

- existing OCI profile credentials for control-plane SDK calls
- identity-domain OAuth credentials for ORDS data-plane access

The control plane continues to use the existing OCI profile mechanism.

The data plane uses the identity domain that is configured on the IoT domain through `db_allowed_identity_domain_host`. The MCP server should read the confidential-application and user credentials for the ORDS token flow from environment variables so callers do not have to pass secrets on every tool call.

Recommended environment variables:

- `OCI_IOT_ORDS_CLIENT_ID`
- `OCI_IOT_ORDS_CLIENT_SECRET`
- `OCI_IOT_ORDS_USERNAME`
- `OCI_IOT_ORDS_PASSWORD`

If these variables are missing, token-minting and all data-plane tools should fail with a structured configuration error.

## Data Plane API Contracts

The design must rely on Oracle's documented IoT ORDS path shape and not invent a custom endpoint layout.

### Base URL

The base URL for the IoT Data API is:

`https://<domain-group-short-id>.data.iot.<region>.oci.oraclecloud.com/ords/<domain-short-id>/20250531`

The implementation should derive:

- `domain-group-short-id` from the first DNS label of `data_host`
- `domain-short-id` from the first DNS label of `device_host`
- `region` from the host pattern, with a sanity check that the parsed value agrees between `device_host` and `data_host` when both are present

### Auth Contract

The ORDS token endpoint is:

`https://<db_allowed_identity_domain_host>/oauth2/v1/token`

The first implementation should use the password grant flow documented by Oracle's IoT ORDS scenario:

- `Authorization: Basic base64(client_id:client_secret)`
- `Content-Type: application/x-www-form-urlencoded`
- `grant_type=password`
- `username=<OCI_IOT_ORDS_USERNAME>`
- `password=<OCI_IOT_ORDS_PASSWORD>`
- `scope=/<domain-group-short-id>/iot/<domain-short-id>`

The token response is expected to contain at least:

- `access_token`
- `token_type`
- `expires_in`

`expires_at` is derived locally as `minted_at + expires_in`.

### Endpoints Used By This Design

The design only relies on these documented endpoints:

- `GET /rawCommandData`
- `GET /rawCommandData/{id}`
- `GET /snapshotData`
- `GET /rejectedData`
- `GET /rejectedData/{id}`

All calls use bearer authentication.

### Filtering Strategy

Oracle's ORDS scenario examples explicitly show `q=` filters against the IoT Data API, for example filtering `rawData` by `digital_twin_instance_id`.

To stay within documented behavior, the first implementation should:

- use documented ORDS query parameters `q`, `limit`, and `offset`
- use `q` primarily for equality filters on `digital_twin_instance_id`
- perform secondary filtering and final sorting in MCP code
- iterate pages until either:
  - enough filtered rows have been collected to satisfy the requested `limit`
  - ORDS reports there are no more rows
  - a hard scan cap of `500` rows is reached

If the hard scan cap is reached before enough matching rows are gathered, return a structured `data_plane_error` with a retry hint to reduce the requested time window.

The first version does not depend on undocumented server-side ordering or comparator semantics.

### Upstream Fields Relied On

`rawCommandData` records:

- `id`
- `digital_twin_instance_id`
- `request_endpoint`
- `request_duration`
- `request_data_format`
- `request_content_type`
- `response_endpoint`
- `response_duration`
- `response_data_format`
- `response_content_type`
- `delivery_status`
- `created_by`
- `time_created`
- `time_updated`
- `time_finished`
- `request_data` on detail reads
- `response_data` on detail reads

`snapshotData` records:

- `digital_twin_instance_id`
- `content_path`
- `value`
- `time_observed`

`rejectedData` records:

- `id`
- `digital_twin_instance_id`
- `endpoint`
- `content_type`
- `time_received`
- `reason_code`
- `reason_message`
- `content` on detail reads

## Domain Context Requirements

Every data-plane tool must be able to construct a canonical IoT data-plane base URL. That requires a canonical `iot_domain_id`, plus the derived context fields described above.

The allowed resolution chain is:

- if the caller provides `iot_domain_id`, use it directly
- if the caller provides a friendly domain selector, require `compartment_id`, resolve the domain, then use the resolved `iot_domain_id`
- if the caller provides a twin OCID, call `get_digital_twin_instance` and use the returned `iot_domain_id`
- if the caller provides a friendly twin selector, require a domain selector first, resolve the twin inside that domain, then use the resolved twin's `iot_domain_id`

This means:

- twin OCID is sufficient for twin-scoped data-plane tools
- twin display name is not sufficient by itself; it must be scoped by domain
- domain display name or domain short ID is not sufficient by itself; it must be scoped by `compartment_id`

## Tool Design

All eight new tools use a single result envelope:

- success: `{"ok": true, "data": ...}`
- recoverable failure: `{"ok": false, "error": ...}`

The output payloads described below are the contents of the `data` field.

### 1. `derive_domain_context`

Purpose:
Return the domain metadata operators need to perform follow-on actions without manually stitching together multiple resources.

Inputs:

- `iot_domain_id`, or
- `iot_domain_display_name` with `compartment_id`, or
- `domain_short_id` with `compartment_id`

Output:

- `iot_domain_id`
- `iot_domain_display_name`
- `iot_domain_group_id`
- `iot_domain_group_display_name`
- `region`
- `device_host`
- `data_host`
- `domain_short_id`
- `domain_group_short_id`
- `db_token_scope`
- any directly relevant access fields already exposed by the SDK

Behavior:
Resolve the domain, read the domain and its domain group from the control plane, derive the normalized context, and return one operator-friendly object.

Derivation rules:

- `device_host`: direct from the IoT domain resource
- `data_host`: direct from the IoT domain group resource
- `domain_short_id`: first DNS label of `device_host`
- `domain_group_short_id`: first DNS label of `data_host`
- `region`: parsed from the host suffix after `.device.iot.` or `.data.iot.` and before `.oci.oraclecloud.com`
- `db_token_scope`: direct from the IoT domain group resource and included for direct database workflows, not for ORDS token minting

### 2. `get_data_api_token`

Purpose:
Return a caller-facing token and expiry metadata for the IoT data plane.

Inputs:

- `iot_domain_id`, or
- `iot_domain_display_name` with `compartment_id`, or
- `domain_short_id` with `compartment_id`

Output:

- `access_token`
- `token_type`
- `expires_at`
- `expires_in`
- the resolved context fields needed to use the token safely

Behavior:
Internally derive or accept domain context, mint the token, and return it to the MCP caller. Token export is explicitly allowed.

This tool does not ask the caller for secrets. Instead it uses:

- `db_allowed_identity_domain_host` from the resolved IoT domain
- confidential-application credentials from environment variables
- IAM username and password from environment variables

If any required credential is missing, return a structured configuration error with code `missing_token_credentials`.

### 3. `get_digital_twin_adapter_full`

Purpose:
Return the adapter fields needed for debugging and migration, not only the current summary subset.

Inputs:

- `digital_twin_adapter_id`

Output:

- all useful current adapter metadata, including:
  - `digital_twin_model_id`
  - `digital_twin_model_spec_uri`
  - `inbound_envelope`
  - `inbound_routes`
  - display name, description, lifecycle, tags, timestamps

Behavior:
Use the existing control-plane `get_digital_twin_adapter` call and map the full SDK model into a stable MCP response.

### 4. `get_raw_command_by_request_id`

Purpose:
Fetch the exact raw command record that corresponds to a request ID.

Inputs:

- `request_id`
- either:
  - `iot_domain_id`
  - `iot_domain_display_name` with `compartment_id`
  - `domain_short_id` with `compartment_id`
  - `digital_twin_instance_id`
  - friendly twin selector plus a domain selector
- optional time window used only as a validation constraint

Output:

- normalized raw command record fields, including request metadata, terminal status, response data, and timestamps

Behavior:
`request_id` is defined as the raw command record `id` from the IoT Data API `rawCommandData` resource.

This tool should:

1. resolve the domain context needed for the data plane using the domain-context rules above
2. fetch `GET /rawCommandData/{request_id}`
3. optionally validate the returned record against the supplied twin selector and time window
4. return the normalized detail record or a structured not-found error

This tool does not search by OCI `opc-request-id`.

### 5. `list_recent_raw_commands_for_twin`

Purpose:
List recent raw command records in a reliable order for operator review and AI follow-up.

Inputs:

- twin selector
- `limit`
- optional time window

Output:

- normalized rows sorted by `time_created` descending

Behavior:
Resolve the twin, query the data-plane raw command feed, normalize records, sort by true creation time descending, and return the limited result set. Do not rely on list order from the upstream API or inferred record IDs.

Contract details:

- if the twin selector is a display name, a domain selector is required
- `limit` default: `20`
- `limit` minimum: `1`
- `limit` maximum: `100`
- time filters use RFC 3339 timestamps
- filtering by twin uses the documented ORDS `q` pattern on `digital_twin_instance_id`
- limit is applied after MCP-side sorting

### 6. `invoke_raw_command_and_wait`

Purpose:
Close the gap between raw command enqueue and raw command outcome.

Inputs:

- twin selector
- `request_endpoint`
- request payload and format
- optional `response_endpoint`
- request duration
- response duration
- timeout

Output:

- immediate enqueue/request metadata
- resolved request ID
- terminal delivery status if observed
- response payload if observed
- timestamps
- timeout indicator if polling expires before a terminal state is seen

Behavior:

1. Resolve the twin.
2. Build the correct SDK request shape for text, JSON, or binary payloads.
3. Call control-plane `invoke_raw_command`.
4. Correlate the invocation with a raw command record.
5. Poll the data plane until:
   - a terminal record is observed
   - the caller timeout expires
6. Return one normalized object that explains both the enqueue step and the final observed outcome.

Payload contract:

- if the twin selector is a display name, a domain selector is required
- `TEXT`: input is a plain string, default content type `text/plain`
- `JSON`: input is a JSON object, default content type `application/json`
- `BINARY`: input is a base64-encoded string, default content type `application/octet-stream`

Binary validation:

- reject invalid base64 locally
- do not invent a local binary size limit in v1; rely on upstream validation and surface upstream rejection cleanly

Correlation contract:

- the OCI control-plane operation does not provide a raw-command record payload
- the MCP tool must correlate by polling `rawCommandData` for the target twin after the invoke call
- a candidate record must match:
  - `digital_twin_instance_id`
  - `request_endpoint`
  - `request_data_format`
  - `response_endpoint` when supplied
  - `request_duration` when supplied
  - `response_duration` when supplied
  - `time_created >= invoke_started_at - 5 seconds`
- if exactly one candidate is found, switch to polling `GET /rawCommandData/{id}`
- once correlation succeeds, expose that ORDS record `id` as the tool's `request_id`
- if multiple candidates remain plausible after the correlation window stabilizes, return a structured ambiguity error and include candidate IDs

Polling contract:

- default polling interval: `2s`
- on `429` or retryable `5xx`, back off exponentially to a maximum interval of `10s`
- `timeout` is the caller-facing hard cap and is independent of `request_duration` and `response_duration`
- `request_duration` and `response_duration` are passed through to the control plane unchanged and echoed in the result

Terminal-state contract:

- terminal success: `COMPLETED`
- terminal failure: `REFUSED`, `EXPIRED`, `NOT_RESPONDED`, `REJECTED`, `BAD_RESPONSE`
- non-terminal/intermediate: `ACCEPTED`, `PREPARED`, `PENDING`, `SENT`, `RESPONDED`

If timeout expires before a terminal state is observed, return the latest observed record with `timed_out: true` rather than pretending the command completed.

### 7. `wait_for_twin_update`

Purpose:
Support post-command or post-telemetry verification loops.

Inputs:

- twin selector
- optional field selector
- `since`
- timeout

Output:

- the first matching update observed after `since`
- full twin snapshot if no field is specified, or field-specific details if one is specified

Behavior:
Resolve the twin, poll the data-plane twin view, compare updates against `since`, and return the first matching change.

Field-selector contract:

- if the twin selector is a display name, a domain selector is required
- the selector is an exact `content_path` from `snapshotData`
- this tool does not support JSONPath or wildcard expressions in v1

Change-detection contract:

- `since` must be RFC 3339
- with a field selector: return the first `snapshotData` record for the twin where `content_path` matches and `time_observed > since`
- without a field selector: return the first observed post-`since` change for the twin and include the current aggregated snapshot rows for that twin at the time of return

Polling contract:

- default interval: `2s`
- same retry/backoff handling as `invoke_raw_command_and_wait`

### 8. `list_recent_rejected_data_for_twin`

Purpose:
Surface ingest failures quickly for troubleshooting.

Inputs:

- twin selector
- optional time window
- optional limit

Output:

- normalized rejection rows including:
  - reason code
  - reason message
  - payload pointers or correlation metadata
  - timestamps

Behavior:
Resolve the twin, query the rejection feed, normalize the upstream payload, filter to the requested twin and time window, and sort recent-first.

Contract details:

- if the twin selector is a display name, a domain selector is required
- `limit` default: `20`
- `limit` minimum: `1`
- `limit` maximum: `100`
- sorting key: `time_received` descending
- filtering by twin uses documented ORDS filtering on `digital_twin_instance_id`
- MCP output should include `reason_code`, `reason_message`, `endpoint`, `content_type`, `time_received`, and the record `id`

## Identifier Resolution

All new tools should support friendly selectors in addition to OCIDs.

### Supported Resolution Modes

- exact OCID
- exact display name for twins, domains, and domain groups
- derived short IDs for domains and domain groups where the value can be deterministically derived from canonical metadata

### Scope Rules

Friendly lookups must be explicitly scoped so the implementation never has to guess across the tenancy.

- twin-friendly lookup requires a domain selector
- domain-friendly lookup requires `compartment_id`
- domain-group-friendly lookup requires `compartment_id`

The resolver should use these control-plane APIs:

- `list_digital_twin_instances(iot_domain_id=...)` for twin lookup
- `list_iot_domains(compartment_id=...)` for domain lookup
- `list_iot_domain_groups(compartment_id=...)` for domain-group lookup

Friendly selector terms:

- twin: `display_name`
- domain: `display_name` or derived `domain_short_id`
- domain group: `display_name` or derived `domain_group_short_id`

### Ambiguity Rules

If a friendly selector matches multiple resources, the tool must fail with a structured ambiguity error. The error payload should include:

- the input that was ambiguous
- resource type
- candidate rows with OCID and display name
- a short next step such as `Retry with the OCID of the intended resource.`

### Not-Found Rules

If resolution finds no candidates, the tool must fail with a structured not-found error that echoes the input criteria.

## Error Handling

Normalize the major error classes instead of leaking raw SDK or HTTP errors as the primary response shape:

- configuration/authentication error
- resolver not-found
- resolver ambiguity
- control-plane upstream error
- data-plane upstream error
- timeout

Each error should preserve enough debugging detail for logs, but the tool output should prioritize actionable guidance for the MCP caller.

### Structured Error Shape

Recoverable tool failures should return a stable error object with this shape:

```json
{
  "ok": false,
  "error": {
    "code": "ambiguous_identifier",
    "message": "Multiple digital twin instances matched display name 'pump-01'.",
    "resource_type": "digital_twin_instance",
    "retry_hint": "Retry with the OCID of the intended resource.",
    "details": {
      "input": {
        "digital_twin_instance_name": "pump-01",
        "iot_domain_id": "ocid1.iotdomain..."
      },
      "candidates": [
        {
          "id": "ocid1.digitaltwininstance...",
          "display_name": "pump-01"
        }
      ]
    }
  }
}
```

Stable error codes:

- `missing_token_credentials`
- `invalid_input`
- `resource_not_found`
- `ambiguous_identifier`
- `control_plane_error`
- `data_plane_error`
- `timeout`

Unexpected programmer errors can still raise exceptions, but user-facing and upstream operational failures should use the structured shape above.

## Compatibility

This work is additive at the tool level.

- existing tool names remain available
- the new tools are added alongside the current ones
- `get_digital_twin_adapter_full` is added rather than replacing the current adapter tool

Internal cleanup may intentionally broaden selected existing outputs where the current MCP unnecessarily drops useful SDK fields. That is an acceptable compatibility change because it is a superset, not a semantic rename.

## Testing Strategy

Testing should be package-local and mostly mocked.

### Unit Tests

Add package-local tests for:

- profile-aware client caching
- twin/domain/domain-group resolution by OCID and friendly inputs
- ambiguity and not-found errors
- domain-context derivation
- token response normalization
- adapter full-model mapping
- raw command polling transitions
- raw command timeout behavior
- recent raw command sorting by timestamp
- twin update wait semantics
- rejected-data normalization

### Integration or E2E Coverage

Add a small number of end-to-end scenarios only for the highest-value flows once the harness can support them:

- invoke a raw command and confirm the tool reports a terminal or timeout outcome
- fetch recent raw commands for a twin

The rest of the behavior should be covered with mocked tests because the package depends on both control-plane and data-plane interactions that are difficult to make deterministic in shared CI.

## Documentation Impact

Update the package README to document:

- the new tools
- friendly identifier support
- ambiguity behavior
- token-return behavior and its security implications
- any required environment or profile assumptions for data-plane access

Security notes:

- never log access tokens, client secrets, or IAM passwords
- do not persist tokens to disk
- do not cache tokens across tool invocations in v1; fetch them in-memory per call to avoid stale or leaked credentials

## Risks and Design Responses

### Risk: control plane and data plane use different access patterns

Response:
keep them in separate internal modules and join them only through normalized domain context.

### Risk: friendly identifiers introduce hidden ambiguity

Response:
centralize resolution and make ambiguity a first-class error, never an auto-pick.

### Risk: `invoke_raw_command` only guarantees request acceptance, not outcome

Response:
the new combined tool must always correlate the initial request with data-plane records before reporting a final result.

### Risk: current single-file structure will become unmaintainable

Response:
perform the internal split as part of this work instead of layering new behavior into the existing file.

## Out of Scope

- touching other MCP server packages
- broad redesign of unrelated existing IoT tools
- adding create/update/delete digital twin workflows beyond what is required for the eight tools above
- introducing interactive prompting in the server itself; errors may recommend next actions, but tool behavior remains request/response
